# Claude Code skill workflows: source-level ownership and lifecycle

## Finding and source scope

There are **two distinct implementation layers**. Claude Code v2.1.282 contains native plugin-evaluation and skill-management code in its bundled executable; the separately installed first-party `skill-creator` plugin supplies authoring/evaluation prompts and helper scripts. The requested CLI is v2.1.282.0 (binary SHA-256 `fc0e3af017705624b9e1bce913f72761864ff994804514da1f5e41380fca4484`); the shell-resolved executable is v2.1.281. Selected minified/transformed JavaScript was recovered from the v2.1.282 Bun bundle, so the CLI is **not wholly opaque**. Original TypeScript, complete source modules, and an application source map were not recovered. The public [v2.1.282 package manifest](https://unpkg.com/@anthropic-ai/claude-code-win32-x64@2.1.282/package.json) identifies a native binary package; it is separate from the plugin version cited below. These recovered binary details are local static-inspection evidence, not a public source-code release.

The locally installed plugin registry identifies `skill-creator@claude-plugins-official` at commit [`6bfd4e0c6d3da6050984fa5ed8281d915fa7ed69`](https://github.com/anthropics/claude-plugins-official/tree/6bfd4e0c6d3da6050984fa5ed8281d915fa7ed69/plugins/skill-creator); its [`plugin.json`](https://github.com/anthropics/claude-plugins-official/blob/6bfd4e0c6d3da6050984fa5ed8281d915fa7ed69/plugins/skill-creator/.claude-plugin/plugin.json) declares Anthropic as author. This plugin commit is not the CLI version and is not claimed to be embedded in either executable.

The local [`ref/anthropics-skills/skills/skill-creator/`](../ref/anthropics-skills/skills/skill-creator/) snapshot matches the installed plugin byte-for-byte for the checked `SKILL.md`, trigger/optimizer/validation/package scripts, and grader/comparator/analyzer prompts. Citations below point to the installed plugin's pinned public source; the separate [`anthropics/skills` `SKILL.md`](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md) is the public instruction source, not CLI source.

## Native CLI paths recovered from v2.1.282

- **`claude plugin eval` is CLI core.** The recovered Bun JavaScript declares the command at file offset `0xd912af8`; its action imports `pluginEvalHandler` at `0xd91e3fc`. Handler `RR` (`0xe138d3d`) validates a target/options and dispatches to suite runner `dc` (`0xe1310dd`). `dc` discovers/validates cases, applies allow-tool filtering and ablation selection, then schedules per-run `Jp` (`0xe134b26`) → `Zp` (`0xe13507a`) → grader runner `xl` (`0xe12aea0`). Grader dispatch `cp` (`0xe12b1fb`) branches across six types: regex, tool-order, tool-used, file-exists, LLM, and baseline. Recovered runner code also contains automatic with/without ablation and a “with Skill” indicator path. Author `scaffold_script` execution is gated by `!noScaffold`; `noScaffold` defaults true (`0xe13a136`), so it is opt-in. Native HTML handling is a separate branch: report handler `hc` (`0xe13b882`–`0xe13b91b`) skips HTML without an explicit report/publish request or a default report directory; otherwise it writes locally and publishes only when account/provider artifact support and feature policy permit, the run is publish-enabled, and it is not an eval-interview session. `--no-publish` disables publication; `--publish-report` explicitly requests it. This is a real CLI-side test harness, distinct from the skill-creator plugin's `run_eval.py` trigger proxy and its Markdown-described subagent trials. These are static observations of minified bundle fragments, not an executed eval or a claim that every option path was traced. The public [HTML-report docs](https://code.claude.com/docs/en/plugin-evals#html-report) likewise describe conditional private-artifact publication; a session-started eval stays local unless explicitly published.
- **Native HTML default:** official [plugin-evals command options](https://code.claude.com/docs/en/plugin-evals#command-options) put `report.html` under `<eval dir>/results/<timestamp>/` by default. Docs say publication is conditional on a Claude.ai subscription with artifacts available; session-started runs stay local unless `--publish-report` is passed, while `--no-publish` keeps the report local. This documentation matches the recovered conditional report handler; it does not imply this report was published.
- **`/skill-doctor` and skill loading are also native.** The embedded command registry defines `skill-doctor` as a local JSX command (`0xc73a9c6`); its report helper (`dGt`, `0xcfbcce4`) gates transcript scanning on `allow_skill_doctor_transcript_scan` before reading the `storageV5` transcript namespace. It reports skill usage/unused status—an audit of usage/context, not a quality grader or skill editor. The bundle also exports `loadSkillsAsPlugins` (`0xcdf1682`) and contains direct Skill-command dispatch that loads `SKILL.md` and appends the user request (`0xcbd81eb`). The precise model-side selection/autoactivation function was not traced.
- **`/goal` has a native prompt-based completion evaluator, not a skill-quality judge.** Handler `YKe` (`0xc0e45d5`) removes a prior goal Stop hook, registers a prompt Stop hook with the requested condition, and stores active goal state. Dispatcher `OIt` routes to `XPt` (`0xc65a11a`), which assembles the condition with recent conversation text (truncated by `Fko`, `0xc65b6c7`) and calls model helper `Bue` (`~0xc65a300`) using schema `cz` (`0xc659d87`): `ok` plus optional `reason`/`impossible`. Verdict handling (`0xc65b0bb`; main loop `0xcc4f750` / `0xcc4fcf5`) clears a met goal, fails/clears an impossible one, or blocks Stop and records an iteration/reason when not yet met. Timeout is separate from these three semantic outcomes. This function-level trace is from the same local binary/hash above; no user transcript was read.
- **First-party authoring/review prompts are a third category.** The public v2.1.282 [`plugin-dev` `skill-reviewer.md`](https://github.com/anthropics/claude-code/blob/v2.1.282/plugins/plugin-dev/agents/skill-reviewer.md#L40-L99) provides a prompt-driven static review after skill creation/change; [`skill-development/SKILL.md`](https://github.com/anthropics/claude-code/blob/v2.1.282/plugins/plugin-dev/skills/skill-development/SKILL.md#L87-L234) guides authoring, validation, and real-use iteration. They are first-party plugin source, not CLI-enforced evaluation logic. Their availability in public source does not establish that `plugin-dev` was installed locally.

## Limits and portability

There is a source-backed Windows portability risk in `run_eval.py`: it passes a subprocess stdout pipe to `select.select()` ([line 108](https://github.com/anthropics/claude-plugins-official/blob/6bfd4e0c6d3da6050984fa5ed8281d915fa7ed69/plugins/skill-creator/skills/skill-creator/scripts/run_eval.py#L108)), while `run_eval()` catches per-query exceptions and appends `False` ([lines 223–225](https://github.com/anthropics/claude-plugins-official/blob/6bfd4e0c6d3da6050984fa5ed8281d915fa7ed69/plugins/skill-creator/skills/skill-creator/scripts/run_eval.py#L223-L225)). A separate bare-pipe probe on this Win32 host failed with `WinError 10093`; it was **not** an execution of this plugin. Consequently a runner failure could appear as “did not trigger,” so Windows scores need an independent runner-health check. The plugin scripts themselves were not run for this report.

An audit of the interrupted session found a third-party Compound Engineering `ce-skill-work` invocation and a session-authored `run_evals.py` using a local ghc-proxy for goal-skill probes. It did **not** observe the official Anthropic `skill-creator` plugin, native `claude plugin eval`, or `/skill-doctor` being invoked. Thus the session's custom A/B/eval work is not evidence that either first-party mechanism ran. No session paths, IDs, credentials, or private prompts are reproduced here.

Neither native eval nor either HTML generator was run for this report, and no HTML was created or published. For native eval, publication is conditional as described above—not an unconditional upload. The creator plugin's separate `run_loop.py --report auto` default writes a temporary report and opens it locally; the separate review viewer can emit static HTML for headless use.

## What transfers to hoa

The most useful portable mechanisms are distinct: native `claude plugin eval` runs isolated with/without-plugin cases and supports deterministic plus model-judged graders; the skill-creator plugin's `run_eval.py` is only a temporary-description trigger proxy; and its creator workflow prompts for user-reviewed, paired output trials. Preserve those boundaries when adapting repeated trigger rates, holdouts, assertions, and benchmark aggregation to hoa. Do not treat either a prompt or the temporary-command proxy as proof of real automatic skill activation.

The repository's current [`hoa-skill-work`](../skills/hoa-skill-work/SKILL.md#L15-L76) and [creation protocol](../skills/hoa-skill-work/references/create.md#L9-L64) start from the observable outcome, actual consumer, target packaging, and evidence needed. Its [evaluation protocol](../skills/hoa-skill-work/references/evaluate.md#L16-L67) requires equivalent fresh contexts for old/new runs, separates discovery from forced execution, uses an independent judge on anonymized outputs, and scales cases to the claim; [`hoa-skill-review`](../skills/hoa-skill-review/SKILL.md#L15-L47) keeps findings read-only and evidence-ranked. Those safeguards are stronger than copying a fixed eval count or assuming a prompt-run proves host behavior. The most suitable extraction is the plugin's *data/benchmark mechanics* behind hoa's existing host-aware evaluation contract—not its Windows-fragile trigger runner or its assumption that prompt guidance has been executed.
