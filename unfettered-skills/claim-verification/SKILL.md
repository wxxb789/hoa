# Claim verification（外部说法先核再用）

## When to Use

- owner 说「先核实一下这个事情的正确性」「这事对吗」「别急着落库」；
- 素材是二手转述（速报 / 汇总 / 翻译帖），而它的结论会被引用或拿去决策；
- 素材内部数字互相冲突，或它自称「官方行为」/「regression」。

目标不是再读一遍帖子，而是回答三个问题：**一手证据里成立吗 / 成立在哪一层 / 有没有反例**。

## 三层核验（按序，别跳）

### 1. 一手口径先落地，并记清事实落在哪一层

- 每个被核的说法都要有一手页面：厂商文档、官方 changelog、原始 issue/PR 正文。取法（raw markdown 出口、GitHub API 取纯文本、changelog）：`references/primary-source-fetching.md`。
- **有日期的 changelog 是判定「policy change 还是 regression」的唯一硬证据**：发布当天就写了 = 不是暗中回归。二手 bug 报告常把「两份文档都没提」当论据，而 changelog 已写 → 该前提当场失效，笔记里要这么写，别跟着它的叙述走。
- **「事实写在哪一层」本身就是发现**：指南 + changelog 常先改，**字段级 API reference 会滞后**（同一字段仍挂着旧描述）。这个不对称解释了「为什么下游客户端继续按旧形状发请求、问题为什么扩散」—— 只写「官方已写明」等于漏掉最有用的那条。
- 引文逐字切片落地（见 `read-later-pipeline` 的引文核验规则），不手抄、不转述。

### 2. 独立复现 ≥3 家，每家必须带对照组

- 只有「新版本坏了」的读数不足以定性；**同一条路径换回旧版本 / 旧形状仍然正常**才算证据 —— 对照组是判据的一半，没有对照组的复现只算半个。
- 复现方要在客户端 / 语言 / 接入层上互不相同（客户端遥测、原始请求抓包、SDK 最小复现、网关上抓出站 body）；同一来源的转述只算一家，别把 N 篇转述当 N 个证据。
- 结论里逐条记「来源 / 复现方式 / 该来源读数」三列，不只给结论句。

### 3. 主动找反向证据，并把「没找到」写出来

- 「已核 N 处官方页 + M 家独立复现，未找到相反的一手证据」是可引用的结论；留白会被下一个 session 重做同一遍。
- 真正核不了的部分显式标注（本账号未实测、需抓出站 body），别让读者自己猜哪句是推断。

## 产物落法

- **正本笔记原地更新**：加一节「正确性交叉核验」（来源 / 复现方式 / 读数表）；把原先靠推断写的句子换成一手原文引文；新来源 URL 进 frontmatter，新抓取命令进 Provenance，让下一个人能重拉一遍。
- **`status.md` 单独记一节（第二轮），不重写第一轮**：官方口径表、独立复现清单、新增发现、新增 evidence 文件 + sha256、更新后笔记 sha256、闸门结果。证据文件进 `~/claw/tasks/<date>/<task>/evidence/<topic>/`。
- 重跑闸门（引文核验 + `markdownlint-cli2`）并回报新 hash 与落点路径。

## 边界与坑

- **需要花钱的复现是 Red**：自有账号实测先给 owner 编号选项，别自己下单；选项里要带免费替代（本地起 stub 上游抓自己 harness 的出站 body，不花钱、纯本地），并说清哪一半属于工程线程。
- **别用二进制里的字符串当结论**：`grep` 到某标识符只说明「有这条代码路径」，判不了运行时行为 —— 写「未定论，需抓出站 body」，别写「我们大概率没问题」。
- 只读的本机证据（config 里的协议开关、安装版本号）可以顺手给，但标明「只读、未实测」。
- 社区 bug 帖的标题与措辞常把未确认行为写成「这是 bug」，引用时按官方口径写，并注明 issue 的开放状态。
