# Install disk hygiene: where the GBs actually are

An install tree is not one artifact. Its size comes from a few accumulators, each with a different
liveness test — and a top-level `du` reports one number for all of them.

## 1. Content-addressed environment snapshots

`~/.hermes/installs/<install-hash>/environments/<env-hash>/` holds one full tree per input
combination (python, node, chromium, cua-driver, venv extras). The install never deletes the ones it
stops using, so a single install directory can hold twenty-odd trees.

- **Liveness comes from a pointer, never from mtime alone.** `facts.json` in the install root names the
  environment in use (`packages.venv.environment`). Everything else in that directory is history.
- **Reclaim set** = siblings the pointer does not name **and** older than the retention window; keep the
  pointer's tree plus the newest one or two so a rollback does not force a full re-provision.
- Discover before concluding: `du -sh <install>/environments/*/ | sort -hr | head`. Concluding "there is
  no old tree to delete" from a listing of the install root is the mistake — the accumulation is exactly
  one level down.

## 2. Package-manager caches: each tool prunes its own choice

| Tool | Where it may live | Prune | Trap |
|---|---|---|---|
| uv | `~/.hermes/cache/uv` (redirected) and `~/.cache/uv` (default) | `uv cache prune` | prunes the tree *it* resolves; set `UV_CACHE_DIR=<dir>` to act on the one you measured |
| pnpm | store dir from `pnpm store path` (`~/.local/share/pnpm/store/vN`); its cache dir is a different path | `pnpm store prune` | measuring one directory and pruning the other reports "freed 0" while GBs vanish elsewhere |
| mise (host toolchain versions) | download caches in `~/.cache/mise/{downloads-cas,npm}`; **installed** versions in `~/.local/share/mise` | delete the cache dirs (re-fetched on demand) | the two trees read alike and are not: clearing `share/` uninstalls live toolchains for the same `du` reading |
| node (build/tool chain) | `node-compile-cache/` under scratch | delete the directory | regenerates on next use; expect the first run afterwards to be slower |

Wrap every prune in a byte count taken **per directory**, before and after its own command. Do not trust
the tool's printed byte total as the effect on your host.

## 3. What only looks reclaimable

- Hardlinked cache entries backing a live venv (`uv cache prune` answers `no unused entries found` while
  the tree stays ~1.5 GB). Reclaiming them means `uv cache clean` = every future install re-downloads.
- Rollback trees the materializer keeps per home (`skills.bak.<ts>`): regenerated by the next
  `--apply`, so delete on the retention clock rather than by hand — and hand the rule to the periodic
  hygiene job, because a rule nobody runs is how they accumulate.

## 4. Doing the deletion

1. Report `df -h /` before and after; every reclaim gets a before → after number.
2. Record path + size + what supersedes it in the batch's deletions file, and treat anything that is the
   only copy of non-reproducible data (`state.db`, `memories/`, raw evidence) as never-delete.
3. Wire the retention into the daily/periodic job rather than leaving it as a documented intention: an
   accumulator with a written-but-unenforced rule regrows to its old size within a quarter. **Read that
   job's own scope statement before calling the reclaim durable** — a deliberately narrow job (one that
   never touches `/tmp` and never anything under the agent workspace) will not touch the accumulator you
   just swept, so a one-off reclaim does not stop the regrowth. Say that plainly, and put the policy
   widening to the owner as a numbered option with its measured size, rather than leaving the impression
   the disk now maintains itself.

## 5. Measure top-down once; never sum a path list

- `du -s` and `--max-depth=1` are mutually exclusive: combined they print
  `du: warning: summarizing conflicts with --max-depth=1` and **nothing else, exit 0** — an empty result
  that reads as "nothing there". Per-child sizes come from `sudo du -xm --max-depth=1 <parent>`.
- Passing a large array of paths to one `du -s` call yields sizes that disagree with a parent-level
  listing: the biggest stale directories came back below a 10 MB filter and survived the first sweep,
  which then had to be redone. Build the keep/delete list from **one parent-level measurement** and
  cross-check any candidate array against it before deleting.
- Rank first, then cut (`awk '$1>=N'`). A threshold applied to unverified numbers silently skips the
  largest offenders — the sweep looks complete while the disk barely moves.
- **Keep every measurement bounded, and never widen a scan to "get it all in one go".** One parent at a
  time (`-x`, `--max-depth=1`), or an unbounded `find / -type f` — which is the command that ends the
  turn (`session turn lease lost`) with the sweep half-done, the owner's in-flight authorization dropped
  and no report written. A scan whose runtime you cannot bound is a dispatched job, not a tool call.

## 6. Host scratch and task trees

- Agent test fixtures turn scratch into a **directory-count** problem as much as a size one (14k top-level
  entries under `/tmp`). Sizes: `sudo du -xm --max-depth=1 /tmp | sort -rn | head -20`; age:
  `stat -c '%y' <path>`; purge directories past the cutoff. For the long tail of small dirs,
  `find <parent> -maxdepth 1 -type d -mtime +N` is the cheap age filter.
- **Name the live users before deleting.** `sudo ls -l /proc/*/cwd | grep -oE '<base>/[^ ]*' | sort -u`
  lists the working directories of running processes — keep those date buckets. `lsof +L1` (or
  `sudo ls -l /proc/<pid>/fd | grep deleted`) finds files already unlinked but still held, where deleting
  more frees nothing.
- Build/module caches a running test is using are safe to empty (go, dotnet, msbuild regenerate; worst
  case a `rmdir` of a busy cwd fails harmlessly) — the real hazard is purging the **current** session's
  own scratch or date directory.
- **A one-off verification workspace is neither a cache nor a task dir.** A `scratch/<something>-verify`
  tree (a materialized copy plus the data subtree it built — GBs, in an afternoon) is referenced by no
  job and survives every cache-shaped sweep, because nothing regenerates it and nothing prunes it. Age it
  like a date bucket: `stat -c '%y'`, check `/proc/*/cwd`, confirm it is neither the current session's
  scratch nor named by a live status file, then delete it and record the size.
- **A package module cache refuses `rm -rf` until write permission is restored.** Go module trees ship
  directories mode 0555 with files 0444, so unlinking inside them fails with `Permission denied` on the
  *files* while the rest of the sweep reports success and the path survives. `chmod -R u+w <path>` first,
  then delete — do not read that first failure as "the directory is protected".
- **Script the sweep per target, and append the manifest before each deletion.** Read-only files are not
  only Go's: hand-made backup archives and npm caches carry them too, and a language-level recursive
  delete (`shutil.rmtree`) raises on the *first* such entry and aborts the whole loop — the run stops with
  the caches already gone and no record of what it removed. Do `chmod -R u+rwX <target>` then
  `rm -rf <target>` per target (unlink needs write on the *parent* directory; `X` spares plain files),
  treat a non-zero return as a finding instead of dying, and write that target's row into the deletions
  file before moving on, so an interrupted run still names what it took.
- **One stubborn path is not a reason for a third approach.** If, after the `chmod` retry, the innermost
  subdirectories still answer EACCES to `stat` while the path is not a mount point (check `/proc/mounts`),
  carries no immutable bit (`lsattr -d`), and is owned by you, stop and report its byte size: it is
  unreclaimable from this host and only the count matters.
- **A directory's mtime is refreshed by any later write inside it**, so an `-mtime +N` filter keeps the
  newest buckets however old their content is. Expect the two or three most recent date buckets to
  survive, and say so in the report instead of listing them as a miss.
- Prefer the tool's own clean to `rm`: `go clean -cache`, `go clean -modcache`,
  `journalctl --vacuum-size=200M`, `apt-get clean`, `pip cache purge`, `uv cache prune`,
  `pnpm store prune`. Downloaded browser binaries (`ms-playwright`, `camoufox`, `puppeteer`) are the
  opposite of a cache win: deleting them costs a re-download and can break browser work mid-task.
- **Host package layers hold their own dead weight.** `snap list --all` marks superseded revisions
  `disabled`; nothing collects them, and a refresh leaves the previous revision on disk at ~0.4–0.6 GB
  each — `sudo snap remove <name> --revision <N>` per disabled row, then re-list to confirm none remain.
  Read the byte delta from `df` rather than summing the per-snap du lines: the two disagree.

## 7. Report shape for a disk sweep

1. `df -h /` before → after as the headline number.
2. One line per reclaimed class with its measured size; name what was kept and why (in-use trees, newest
   date buckets, rollback points).
3. **Manifest before an irreversible purge**: `find <dirs> -type f -printf '%s\t%p\n' | gzip >
   <backups>/purge-manifest-<label>.tsv.gz`, then print file count + total bytes. A 12 GB tree's manifest
   is ~1 MB and is the only provenance left afterwards; a deletions file alone cannot answer "what was in
   there".
4. Split the findings into **free wins** (caches, logs, build artifacts, retired toolchains — just do
   them) and the **decision tier** (task/evidence dirs, downloaded binaries, snapshot/rollback trees), and
   put only the decision tier to the owner: 2–3 numbered options, each with its measured size, the
   recommended one first.

## 8. The age-based sweep as a standing gate

Once `/tmp` and the agent workspace enter a job's scope, age becomes the eviction rule, and four things
decide whether it is safe.

- **A unix socket's mtime is its creation time, forever.** A socket that has been serving for three weeks
  is age-identical to an orphan, so an mtime filter alone eventually unlinks a live socket — its holder
  keeps working while every new connect fails. Gate on liveness, not age: collect the paths held open
  right now (`os.readlink` over `/proc/[0-9]*/fd`, plus the paths in `/proc/net/unix`) and skip any entry
  that is, contains, or sits under a held path.
- **Age an entry by the newest mtime anywhere inside it**, not by its own: a directory's mtime stops
  moving once the writes go a level deeper, which is exactly what a detached run does. Walk it yourself
  (`os.walk`, never descending into symlinked dirs) and treat "newest thing inside is older than the
  window" as the only delete signal.
- **Ownership and system prefixes are hard exclusions.** Skip any entry whose uid is not ours — root
  services park their private trees in `/tmp` — and the `systemd-private-*`, `snap-private-tmp`,
  `.X11-unix`/`.ICE-unix`/`.font-unix`/`.XIM-unix` names by prefix. Unlinking someone else's file is not
  a disk win.
- **Dead sockets free dirents, not bytes.** Every one reports `0` to a per-path size sum, so a
  byte-thresholded report stays silent while `/tmp` climbs toward a thousand entries. Count them as
  items removed; keep the byte threshold for the message gate only.

Three consequences ride along with the widening:

- **Retention is meaningless unless the cadence is at least as fast as the window.** A 3-day retention
  enforced by a weekly job is a 3-to-10-day retention — state the *effective* window, not the configured
  one. When the owner's complaint is fill rate, tighten the cadence rather than adding another job: a
  sweep below its report threshold is silent, so a daily run costs no attention.
- **Edit the job's own scope statement in the same change.** The docstring line that lists what the
  script will never touch (a hard promise like "never anything under the agent workspace") is now wrong,
  and so is every repeat of the job's name and schedule: the skills' cron table and the generated live
  inventory. Rename when the cadence changes — `weekly disk reclaim` firing daily is a name that misleads
  the next audit.
- **Prove the gate through the runtime**: `hermes cron run <id>`, then read
  `cron/output/<id>/<timestamp>.md` — `Status: silent (empty output)` is the evidence that a clean run
  costs no message and exits 0.
