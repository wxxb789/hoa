# Hermes profile independence

## When to Use

| You hear / see | Do |
|---|---|
| "每个 bot 应该独立演进"、profile 继承了 root 的 SOUL | identity section below |
| profile 的 `skills/` 全是符号链接、改一处全舰队变 | skills section below |
| 某个 bot 要给自己改技能 | `evolvable_skills` / fork rule 2 |
| `profile-layer-reconcile` 或 `contract-drift-check` 报 SOUL/skills 漂移 | run the two `--check` commands |
| 漂移报告大片全红，但你只动过无关文件 / 该 repo 刚被解冻 | rule 18（先找暂停记录，再判回归） |
| NRS 线换个角色定义 / 改白名单 | edit the repo binding, then `materialize.py --apply` |
| 改名 / 新建 / 退休一个 home | §Profile lifecycle |
| 加/删 home 之后备份报 `policy-stale` | §5 of the checklist reference |
| 要证明备份能跑（不只是 hash 对）/ 月度 produce 之后 | Commands 里的 restore drill |
| 某个技能在 home 里静默消失 / `--check` 报 `MISSING` | rule 10（上游改名留下悬空链接） |
| 某个技能在 host 池里是实体目录、`install_host_skills --check` 报 `drifted` | rule 12（先判方向：退休还是回流） |
| 要让 default home 真正用上某个技能（没出现 / 名单里有死名） | rule 13（`allowed_skills` + `skills.disabled`） |
| owner 要一次 fleet 级只读审计：本应做没做 / 潜在风险 / 效率 | `references/profile-layer-audit.md`（工具顺序 + 每类结果怎么读） |

**Not for**: gateway restart mechanics → `hermes-gateway`; scheduling → `hermes-cron`; model routing →
`hermes-models`. Full ordered migration + rollback: `references/profile-refactor-checklist.md`.

Each Hermes profile is its own HERMES_HOME. Since the 2026-11 de-inheritance refactor, **nothing
is inherited**: no generated SOUL.md, no symlinked skill library. A profile that quietly inherits
Zoe's identity or the root skill pool is a bug, not a default.

## Model

| Layer | Owns | Where the truth lives |
|---|---|---|
| Identity | `profiles/<p>/SOUL.md` (owned, hand-editable) | `<private-repo>` for Zoe-line homes; `<research-repo>` `bots/roles/` for `*-nrs` |
| Security contract | `core-invariants` head block at **byte 0** of every SOUL — **one source per line** | Zoe line: `~/.hermes/contracts/core-invariants.md`; NRS line: repo-owned, under `bots/roles/` |
| Skills | real files, only `profile.yaml: allowed_skills` | `~/.hermes/skills/` (host pool), `<research-repo>/skills/` (NRS-only), `hoa` (generic/portable) |
| Provenance | `profiles/<p>/skills.lock.json` (source, tier, upstream tree hash, mode) | regenerated by the materializer |
| Data | `state.db`, `memories/`, `sessions/` | local only, never in git |

Two control planes, one writer each: **Zoe line** (default, forge, gray, career-coach, studio, eva) → `<private-repo>`;
**NRS line** (`*-nrs`) → `<research-repo>/bots/bindings/hermes/materialize.py`. Never let both write
the same home.

## Two independent lines; the only shared surface is skills

Standing owner directive: the Zoe line (`default`, `forge`, `gray`, `career-coach`, `studio`, `eva`) and the NRS
line (`*-nrs`) are **separate products**, not one family with per-role overrides.

1. **No cross-line reuse of profile setup.** An `*-nrs` home must not take the host's behaviour
   contract, identity prose, cwd or tool defaults; the Zoe line must not be written by the NRS
   generator. Profile-level overlap is not permission to share.
2. **Each line owns its security contract.** Keep `core-invariants` as a per-line source — host file
   for the Zoe line, repo-owned file for NRS — with the same byte-0 head-block mechanism. Do **not**
   single-source it across lines "for consistency": independence is the requirement, and the shared
   file is the thing being removed.
3. **Skills are the one shared channel, bidirectionally.** A capability that proved generic (portable,
   no host literals) is promoted to the generic pool (`hoa`) and materialized into whichever homes need
   it; a line-specific skill stays in that line's pool. Sharing happens by promotion, never by copying
   one home's tree into another home.
4. **A bot's SOUL is its own document, not "front-door identity + a role override".** Copy-based
   de-inheritance still leaves the full front-door identity in every main-line home with a role section
   bolted on — on the order of 2.7 of 4.5 KB duplicated. Rewrite it minimal and role-first: identity,
   job, do / do-not, gates, execution + verification, memory routing, output, tone. Drop the front-door
   sections that bot cannot act on. Template: `templates/role-soul-minimal.md`.
5. **Do not propose compiling a shared identity core into every home.** Single-sourcing the generic
   sections and regenerating them across homes was explicitly rejected: it re-creates the coupling
   independence is meant to remove. A rule that has to reach several bots *inside one line* is a
   contract block (rule 3 below) or a repo-owned shared behaviour file — never a new cross-home
   generator.

Separation work runs one item per pass, each with its own verification: baseline SOULs + `AGENTS.md`
into a backup dir → rewrite the main-line SOULs from the template → move each bot's `terminal.cwd` to
its own workspace with a short pointer-style `AGENTS.md` → decouple the NRS generator from host
contracts → give each line its own drift check → confirm the skills pool is the only thing both lines
read.

### Proving a separation step (never report it from intent)

- **cwd → contract split.** Run the same bot from two directories and ask which first heading it sees:
  `cd ~/claw/bots/<bot> && HERMES_HOME=~/.hermes/profiles/<bot> hermes chat -q "你读到的 AGENTS.md 的第一个一级标题是什么？只回标题本身。" --oneshot -t clarify -Q`,
  then repeat from `~/claw`. Two different headings = the split is real. A CLI probe inherits the *shell*
  cwd; gateway turns use `terminal.cwd` from the profile config — so `cd` first or you are testing the
  wrong thing.
- **Regenerated identity.** `sha256sum ~/.hermes/profiles/*/SOUL.md` before and after you change the
  generator's invariants source. Byte-identical output is the evidence that the swap changed no
  behaviour; if the marker text itself has to change, print that diff and declare it instead.
- **Line-owned invariants.** Once the NRS line compiles from its own file, scope
  `profile-soul-deinherit.py --check` to the Zoe line (`h.name not in ROLE_HOMES`) or it reports
  permanent drift on homes it no longer governs.
- **Byte counts, not adjectives.** Report the before/after size of each SOUL and of each bot's
  `AGENTS.md`; "much leaner" is not a result, "8890 B → 3290 B" is.

## Profile lifecycle: create, rename, retire

`hermes profile create|rename`, the five bootstrap files, and the rename sweep list (drift
checkers, recovery policy, cron ownership tags, gateway restart order) live in
`references/lifecycle.md`. Use the CLI, not hand-assembly: a `mv` leaves routing identity behind.
Backup retention tracks (generation rollback vs. the per-change `<file>.bak-<what>` copies kept inside
that change's own `cleanup-<date>/` batch) live in the same file — there is no separate `pre-change-*` tree.

## Commands

```bash

# which turns a read-only audit into a ModuleNotFoundError mid-flight. The check scripts now re-exec
# themselves onto a capable interpreter (`lib/interp.py::ensure_runtime`, shell side `lib/py.sh`), so a
# ModuleNotFoundError from one of them means the guard is missing or bypassed — not that the check failed.
PY=~/.hermes/hermes-agent/venv/bin/python

# identity
python3 ~/.hermes/scripts/profile-soul-deinherit.py            # plan / dry run
python3 ~/.hermes/scripts/profile-soul-deinherit.py --apply [--only <home>]
python3 ~/.hermes/scripts/profile-soul-deinherit.py --check    # head-block byte prefix

# skills (atomic swap; exactly one skills.bak.<ts> rollback tree per home)
python3 ~/.hermes/scripts/profile-skill-materialize.py --dry-run
python3 ~/.hermes/scripts/profile-skill-materialize.py --apply [--profile <home>]
python3 ~/.hermes/scripts/profile-skill-materialize.py --check
python3 ~/.hermes/scripts/profile-skill-materialize.py --contract-version   # gate for repo-side callers
python3 ~/.hermes/scripts/profile-skill-materialize.py --prune-duplicates [--dry-run]  # bundled-sync duplicates

# daily housekeeping (wired into the 05:00 health job; silent when clean, one ZH line per action):
#   relink_hoa_skills()      — re-link declared-but-absent skills from the pool (rule 10)
#   rematerialize_drifted()  — re-apply homes whose ONLY guard verdict is upstream drift (rule 15)
#   host_library_gaps()     — remove empty category dirs, report ~/.agents vs .skill-lock.json gaps
#   prune duplicates + stale install environments + package caches; expire
#                              ~/claw/backups/cleanup-YYYYMMDD older than --keep-days (default 30)
python3 ~/.hermes/scripts/daily-hygiene.py [--dry-run] [--keep-days 30] [--json]

# both layers (silent when healthy)
python3 ~/.hermes/scripts/profile-layer-reconcile.py --dry-run
python3 ~/.hermes/scripts/contract-drift-check.py

# two-week review metrics (all homes; NRS-compiled sections are tagged, --zoe-only narrows the view)
python3 ~/.hermes/scripts/profile-independence-metrics.py [--json] [--zoe-only]

# restore drill: boot every home in a generation and verify SOUL/.env against manifest.json
# (~15 min for 11 homes; report at ~/.hermes/logs/recovery/drill-*.md). The script deletes each copy and
# its profile registration itself — per home on the happy path, and by `trap … EXIT INT TERM` when the run
# is interrupted or a boot fails — so a finished drill leaves no `drill-*` directory and no phantom id.
# Verify that claim anyway: leftover empty `drill-*` directories are an observed failure mode, and
# `hermes profile list` never shows them, so only a directory listing does.
# `ls ~/.hermes/profiles/` minus `hermes profile list` = the ghost homes to clean.
# Pass `--keep` to inspect a copy deliberately; that run prints the paths and you remove them by hand

bash ~/.hermes/scripts/restore-drill.sh [<generation-dir>] [<home> ...]

bash ~/.hermes/scripts/hermes-recovery-drill.sh
```

## Rules

0. **Advisory review is a step, not a mood.** Before reporting a large step as done, run one review by a
   different model family (this fleet: `pi -p --no-tools --no-skills --model ghc-proxy-chat/gemini-4-carbon
   --thinking high @prompt.md`) and fix its findings before the report. Carbon reviews the *plan*, not the
   diff; CI plus Codex review the diff.
1. **Changing a bot's skill surface** = edit its `allowed_skills`, then `--apply`. Never hand-place a
   skill dir into a profile; the next materialize deletes it.
2. **Per-bot skill fork** = add the name to `evolvable_skills` (writable from the start) or flip
   `status: forked` in `skills.lock.json` before editing. Managed copies are 0444/0555 on purpose;
   chmod them writable only through that path, otherwise redistribution cannot tell intent from dirt.
3. **Contract change** (security/gates/ADHD/GEPA) goes to `contracts/core-invariants.md` first, then
   the head block is **replaced in place** in each SOUL — and never by `--apply`. Ownership detection
   keys off `text.startswith(block)` + the `owned-by-this-home` marker, so once the block no longer
   matches, `--apply` treats the file as un-seeded and rebuilds it from the root identity, silently
   destroying that home's body. Replace the block text, re-run `--check`. The same trap fires when you
   hand-rewrite a SOUL into a shorter document: keep the block byte-identical at byte 0, or the next
   `--apply` overwrites the new body.
4. **Identity change** stays inside the home that needs it. There is no propagation generator; a rule
   that must reach several bots is either a contract (rule 3) or a repo-owned shared behaviour file.
   **A convention the owner states for the whole fleet takes the same route plus a mechanism.** A rule
   about *how* work is done ("scripts are written in one of these three runners", "specs start from X") is
   followed from whichever copy a session loads, so it goes into each line's own operating protocol — this
   host's `~/claw/AGENTS.md` for the Zoe line, the receiving repo's own `AGENTS.md` for work done in that
   repo — never injected into a compiled SOUL, which changes identity for every home at once for a rule
   nobody needs in their identity. Then add it to the skill governing that class of work and to the
   checklist that gates anything shipped outward, pair it with the grep or gate script that enforces it,
   and hand that mechanism to the lane owning the outward artifact: prose with nothing to act on it gets
   skipped on the first busy day. Finish by grepping the rule's own distinctive phrase across every file
   you claim to have landed, not by trusting the edit list. **Which layer a rule belongs in is decided by
   priority × importance × change frequency** — the more important and the rarer a rule, the higher it sits,
   so a high-frequency operative never lands in an owner-gated file where every correction blocks on
   approval — and the file is written for its actual reader, a model: terse, no human-readability tax, and
   omitting anything the reader can obtain by calling a tool. Layer model, ban list and the laundering trap:
   [layer placement](references/instruction-layer-placement.md).
5. **NRS line**: role text lives in `bots/roles/<role>/ROLE.md`, common behaviour in
   `bots/roles/_shared-behaviour.md`. `materialize.py --apply` is idempotent; hand edits to an
   `*-nrs` SOUL.md are drift and will be overwritten. It also calls the host materializer itself, so a
   binding change is enough — do not run the two scripts by hand. `host_reconcile_hook.py`'s reverse
   skill policy (`skills.disabled` complement, NRS managed block) is retired: expect no writes there.
6. **Config-ization already has a canonical contract — do not invent one.** `hoa` owns it:
   `skills/skill-porting-and-publishing` (five de-coupling axes, "configuration is a gate" section) and
   `scripts/skill_config.py` (`resolve(skill, key, flag=, env=, default=)`). The chain is
   `CLI flag → env → $XDG_CONFIG_HOME/<skill>/config.yaml → documented default`, and a key already shaped
   like an env var (`SKILLS_HUB`) keeps that name. A skill documents the knobs in a `## Configuration`
   table pointing at that section — a private scheme such as `skills.globals.*` in Hermes `config.yaml`
   is drift, not configuration.
   **Private (never-published) business skills are the other tier and take the opposite shape:** one
   shared `topology.yaml` (repo roots, channel/handle ids, semantic model tier) tracked by `<private-repo>` and
   read by every private skill — *not* one `~/.config/<skill>/config.yaml` per skill. N copies of the same
   channel id become N sources of truth, and `$XDG_CONFIG_HOME` sits outside the recovery policy, so the
   config plane must be added to the backup inventory before skills start depending on it. Configure only
   environment bindings: repo-internal structure (`garden/`, `studies/OPEN-ITEMS.md`), business enums
   (`wip/review/done`, `E0/E1/E2`) and credentials are the contract itself, not knobs — credentials go in
   env/secret stores with no fallback, never in a YAML default.
7. **Migration order** that works: retire the old writers → build `skills.next` → swap with two renames
   → restart the gateway. Building in place inside a running gateway shows a partial skill set, and a
   second run over 0444/0555 copies raises EACCES.
8. **Before `git reset --hard`, check whether the dirty file already lives on a branch or PR.** An
   uncommitted copy is often a duplicate of work already pushed (`gh pr list --state open`, `git log
   origin/HEAD..`); the reset then only removes the duplicate, not the work. Confirm which before
   reporting a loss — and confirm it before wiping.
9. **A repo that mirrors one global `VERSION` into every skill turns N port PRs into N conflicts.**
   Land them serially (one branch at a time, rebase between), and rebuild any long-lived branch on
   current `main` rather than resolving the mirror files by hand.
10. **A rename — or any path change — in the shared pool breaks homes silently — three steps, every time.**
    A skill renamed or *moved* (e.g. into a category directory) upstream (hoa, a repo binding, a bundled
    update) leaves the host library's symlink pointing at a
    path that no longer exists, and `os.walk`/`leaf_index` skip a dangling link without an error: the
    materializer reports `MISSING(1)`, drops the skill from that home's disk, and only
    `skill-applyback-guard.py` says `source missing`. So after any rename: (a) rebuild or delete the
    host-pool link, (b) sweep for dangling links —
    `python3 -c "import pathlib;r=pathlib.Path.home()/'.hermes/skills';print([str(p.relative_to(r)) for p in r.rglob('*') if p.is_symlink() and not p.exists()])"`,
    (c) `grep -l <old-name> ~/.hermes/profiles/*/profile.yaml`, edit those `allowed_skills`, then
    `--apply --profile <home>` and `--check`. Do (c) even when the new name seems obviously equivalent:
    the whitelist is the only thing that keeps the capability on disk. (d) Sweep the **deny** list too:
    `grep -rn '^\s*- <old-name>$' ~/.hermes/profiles/*/config.yaml`. `skills.disabled` entries keep the
    old string, so the rename does not just lose a skill — it silently *enables* one those homes had
    switched off, and nothing reports it. Rewrite those lines in the same pass (backup each file first),
    then verify the count of the old name is 0 across both files and the new name appears the same number
    of times. The 05:00 health job carries the
    same test as `skill_wiring` (`_host_skill_index`): declared-but-absent names and dangling host links
    are reported the next morning even if nobody noticed the rename.
    **No rename is needed for the same silent loss:** a skill newly ported into the shared pool and added
    to a home's `allowed_skills` while nobody creates the pool link resolves to nothing, and the stale
    copy the home already holds keeps serving. Heal it by construction, not by hand — `daily-hygiene.py`'s
    `relink_hoa_skills()` walks every home's declared names, finds the ones absent from the pool, and
    links them from the repo, taking the category from the skill's own `metadata.areas` first token
    (never from its name). When you write that "is this name in the pool?" check yourself, prune
    dot-directories from the walk: `.archive/` and curator backups hold retired copies, and counting
    them as present makes an archived skill look alive while every home declaring it reads `MISSING`.
11. **Review metrics count every home — label what a generator produced, do not narrow the population.**
    `profile-independence-metrics.py` measures two numbers: `forked`/`evolvable` skills older than 7 days,
    and SOUL sections duplicated verbatim in ≥3 homes. The owner's口径 is **all homes**: quietly restricting
    the population to the Zoe line makes the number look better and answers a question nobody asked.
    `*-nrs` homes compile from one repo-owned behaviour file, so their identical sections are tagged
    `NRS 单源` in the output and read as "the single source working", not as debt to fix; `--zoe-only`
    exists for a side-by-side comparison. Same shape for any future cross-home metric: name the
    population in the report and tag generator-produced agreement.
12. **A real directory in the host pool shadows the canonical repo — decide the direction file by file.**
    `install_host_skills.py --check --root ~/.hermes/skills` reports these as `drifted:` and refuses to
    re-link them, so the skill keeps running from the stale copy while the catalog drifts further. Two
    classes, opposite fixes: (a) a superseded hub/bundled install that is **not** in `allowed_skills` →
    retire it (back the directory up out of the pool, then remove it — do not re-link); (b) a live
    host-authored copy that is *ahead* of the catalog → port the host's **body** into the catalog while
    keeping the catalog's frontmatter schema (its checker owns those fields), port the host-only
    `references/` / `scripts/` / `templates/` files with it, then re-link. Direction is per concern, never
    per skill: diff both sides and count lines — a frontmatter/format-only diff means the catalog is
    current, a host-only file or hundreds of body lines means the host is. Blanket-copying either way
    either loses live work or publishes stale content. Ported host prose is also where the portability
    findings live — sweep it before it lands (skill `skill-generalization-gate`, its
    portability-sweep reference).
13. **Enabling a skill for the default home is two files, and one of them rewrites itself.**
    `~/.hermes/profile.yaml: allowed_skills` is the declared surface; `skills.disabled` in
    `~/.hermes/config.yaml` is what the default home actually loads. Add the name to the whitelist, remove
    it from the disabled list, then confirm with `hermes skills list` (`enabled`). Sweep for dead names in
    the whitelist in the same pass: a skill renamed or deleted upstream stays in `allowed_skills` and
    reads as configured while resolving to nothing. Editing `config.yaml` through a YAML round trip
    (`safe_load` → `safe_dump`) drops comments and re-wraps long scalars, so a line diff is unreadable:
    back both files up first, then verify **semantic** equality by walking the two parsed trees and
    printing only the changed keys. A large diff that changes one list is correct; a small diff proves
    nothing.
14. **Never assemble a home in place under `~/.hermes/profiles/` — stage outside, hand it over with one
    rename.** The gateway watches that directory and opens a new home's `state.db` the moment the
    directory appears, so a home being written file-by-file is read half-written: SQLite answers
    `database disk image is malformed`, the profile is parked as `profile_parked (session store
    unusable)`, and because the park reason is read from a **cached** open failure, every later attempt
    repeats it after the extracted file verifies clean — a healthy backup looks rotted. Extract to
    `~/.hermes/cache/scratch/drill-stage/<name>`, write `profile.yaml`, disarm `cron/jobs.json`, then
    `mv` the tree into place (same filesystem ⇒ atomic). Applies to every path that materialises a home
    — restore drill, recovery restore, clone/migrate, manual recovery — and to any file written into a
    live home's tree. Diagnosing it when you meet the verdict:
    `python3 -c "import sqlite3;print(sqlite3.connect('file:<db>?mode=ro',uri=True).execute('PRAGMA integrity_check').fetchone())"`
    plus a sha256 against the backup's `manifest.json`; `ok` + matching hash beside a `malformed` verdict
    means the reader raced the writer.

15. **Auto-repair of skill drift must be narrower than "re-apply everything".**
    `skill-applyback-guard.py` emits one verdict that means *upstream moved ahead* (`source drifted from
    the materialized copy`) and several that mean *a person has to decide* (`live tree … != lock …
    (silent edit?)`, a writable managed file, two sources claiming one name, `locked but missing on
    disk`). `daily-hygiene.py`'s `rematerialize_drifted()` re-applies a home only when every failure for
    that home is the first kind and prints `需人看：<verdict>` otherwise, so an undeclared fork keeps
    failing loudly instead of being silently overwritten by upstream. Keep any future auto-heal on that
    shape — classify the checker's verdict, act on exactly one class, leave the rest as alarms — and
    prove both directions with a fixture before trusting it: append a byte to a pool-side source (⇒ the
    home is re-applied) and to a materialized copy (⇒ reported, left untouched).

16. **Restoring a pool skill that upstream pruned: re-vendor from git, and count the archive's path components.**
    When a canonical repo (hoa) removes skills the homes still declare, the pool keeps a dangling
    symlink and every home silently loses the skill. Restore it as a real dir in the pool from the
    repo's history, then re-materialize the declaring homes — do **not** delete the declarations:
    the capability was never revoked, the source just moved. Two mechanics that bite:
    - `git -C <repo> archive <rev> skills/<name> | tar -x --strip-components=1 -C <pool>/<category>`
      — **1**, because the archive path is `skills/<name>/…` and you are extracting *into* the
      category dir. With `2` the skill's own files land in the category dir itself (`<category>/SKILL.md`),
      which both loses the skill *and* makes the category look like a skill; verify with
      `<pool>/<category>/<name>/SKILL.md` existing and a re-run of the materializer's `--check`.
    - Which source to restore from, in order: the Hermes install (`hermes-agent/skills/<cat>/<name>`
      = bundled; `hermes-agent/optional-skills/<cat>/<name>` → `hermes skills repair-official <name> --restore`),
      then the repo's history. A bundled/optional restore must unlink the stale pool symlink first,
      or `repair-official` dies on `FileExistsError`.
    After any such repair, the *checks* must agree: `profile-skill-materialize.py --check` clean **and**
    the daily health `skills` class empty. Two exemptions the materializer applies and the health
    checker must mirror, or a repair reads as a regression the next morning: a **category shell**
    (dir with no `SKILL.md` at or under it — distribution ships `DESCRIPTION.md` into homes) is not an
    undeclared copy, and a **forked/evolvable** copy (`status: forked` in `skills.lock.json`) is the
    bot's own, so its mode and tree hash are deliberately not compared.

17. **A shell write to an instruction file bypasses the tool-layer approval gate — keep the `pre_tool_call` guard armed.**
    `write_file`/`patch` route `AGENTS.md`/`SOUL.md`/`MEMORY.md`/`USER.md`/`HERMES.md`/`CLAUDE.md` writes
    through the owner's approval card (`tools/file_tools_write_guards.py`), and the command-level detector
    (`tools/approval_detection.py`) covers credentials, `~/.hermes` config and lifecycle — but **no
    instruction file**. So a heredoc/`python -c`/`tee`/`sed -i`/`cp` write went through both layers
    silently. The host fix is the `hooks.pre_tool_call` guard `protected-write-guard.py`
    (`~/.hermes/config.yaml` + `shell-hooks-allowlist.json`); it is best-effort by design (string-level
    detection is not sound — variable indirection is covered, obfuscation is not), so treat it as a
    guard rail and route instruction-file edits through the file tools. When adding a hook to a
    **running** gateway, the allowlist entry is what makes a non-TTY gateway register it (no prompt,
    no restart): write the config block *and* the `{"event","command"}` allowance, then confirm
    `hermes hooks list` says `✓ allowed` and `agent.log` logged `shell hook registered`.

18. **A drift report can be the *result* of a deliberate pause — find the pause record before calling it a
    regression.** A freeze record (`~/.hermes/state/skill-upstream-pause.json`: a per-repo `paused` list with
    `since`, plus the reason string) suppresses upstream→home rematerialization for that repo, so every
    declared skill still on an older tree reports as drift and the daily checker goes red *by design*. A red
    list whose members are exactly that repo's skills, with none of your own edits implicated, is the freeze
    working. Two rules for lifting one: (a) size it with the trigger's own dry-run —
    `python3 ~/.hermes/scripts/skill-rematerialize-trigger.py --repo <repo> --since <the record's date> --dry-run`
    — and report homes × skills; call out any home carrying the `live tree … != lock … (silent edit?)` verdict,
    because rule 15's auto-heal refuses exactly those, so lifting the pause re-alarms them instead of
    repairing them; (b) a pause that a host toolchain honours is **not** covered by "sync this repo" — one
    owner sentence about the git side is not consent to write into every home, so report the blast radius and
    ask. Resume mechanics belong to the record itself: delete the file (or its entry) and the next trigger run
    pulls the owed drift back.

19. **Take a drift verdict from the checker, not a hand-rolled scan — and re-run the checker before acting.**
    The host pool holds skills as symlinks into the canonical repo, so a walk that does not follow links
    (`Path.rglob` before 3.13 does not descend a symlinked directory) reads every linked skill as missing on
    disk and reports a fleet-wide `MISSING` that does not exist — the inverse of rule 12's shadowing, and the
    reason a hand-rolled scan "found" drift on every home. Run `profile-skill-materialize.py --check` and
    `contract-drift-check.py` and report *their* verdict; keep your own scan a hypothesis you confirm against
    them, follow links if you walk by hand, and name the command you ran. A drift list from earlier can also
    already be stale — `daily-hygiene.py`'s `relink_hoa_skills()` and `rematerialize_drifted()` (rule 10)
    repair declared-but-absent and upstream-drifted skills — so re-run the checker before sweeping for fixes.
