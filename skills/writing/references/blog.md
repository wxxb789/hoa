# Technical blog

For dev blogs, engineering write-ups, deep-dives.

> **The publishing site's own contract wins over this file.** A blog repo normally carries a style
> guide (bans, house voice), a series/topic brief, and a pipeline note (which model writes, how drafts
> are named, how a release is verified). Read all three first; where they disagree with this file, they
> win — this file describes the form, the site describes its own mechanics.
>
> **Final drafts run in a clean context at low reasoning effort.** A one-shot, tool-less call with a
> prompt file is the right shape: no session history will fill in what the prompt forgets, so the
> prompt must carry the reader, occasion, material, constraints, and taboos itself. Run long
> generations in the background and wait on the completion notification instead of blocking a
> foreground shell.
>
> **低推理档，不是高推理档**。写作终稿一律 low：开高会让模型在写每句话前反复权衡，交出来的东西
> 更工整、更均匀、更像算法排的版。高推理档只用于写前规划、评审契约、诊断这类“想”的任务，不用于
> 成稿。
>
> **clean context 的代价是 prompt 必须自带全部背景**：读者、场合、素材、约束、忌口，缺什么都不会
> 被“会话历史”补上。迭代协议分两种：
> - **大改（换结构、换角度、重写）**：只给问题清单 + 素材 + 结构指定，**不喂上一版正文**。给了它就会
>   沿着旧句子改，旧问题跟着回来。
> - **细节改（改数字、压句长、修某段、换标题）**：给完整上一版 + 逐条改动项，它才不跑偏。

## 单位是系列，不是文章

- 一篇 = 一个决定。系列 = 一串决定，读者按顺序做完才算解决问题。话题大到一篇文章装不下时，
  不要压缩，拆成系列并用双向链接串起来。
- 拆篇判据只有一条：核心主张能不能一句话说完。需要用「并且」连接两个主张，就是两篇。不看字数，
  也不看单节可删性（反例、边界、背景删掉后主论点都不塌，按那种判法文章只剩提纲）。
- 单篇没有字数上限，也没有下限：材料只够 1,200 字就写 1,200 字，不许为凑长度加过渡段、复述或
  背景铺垫。唯一的上限是主张数量。

## 双链契约

站点若渲染 backlinks（反向链接），就用它做系列导航。

- 结论自包含：没读前一篇也能读懂这篇的结论。前置概念不外包：主篇给三行最小定义，链接只用于
  展开论证（只给链接会让新读者直接掉队）。
- 锚文本写清点过去能得到什么，禁用「详情见这里」「如上所述」。
- 每篇末尾固定三条：上文（读者为什么走到这里）、下文（下一步看什么）、旁支（另一个角度）。
- 例外：系列首篇只放「上文」一条——站上还没有可指的下文与旁支。下一篇发布时把三条补齐，并回填已发那篇。
  先发再补的代价远小于攒着不发；规则要为“第一篇”留出口，否则第一条永远发不出去。
- 不建索引页，也不用 tag 归档系列：系列靠「上文 / 下文 / 旁支」三条链接自然生长，读者从任意一篇
  顺着 backlinks 走。
- 系列名是这一串文章的名字，不是每篇的标题。每篇有自己的标题；禁止用系列名、编号（010203）、
  「系列之三」当标题。

## 图与外链

机制、架构、原理类文章至少配一张自制图。

- **优先 mermaid，不用截图**：站点在构建期渲染 mermaid，改一处文字不会让整张图作废；截图每次改版都要重截，
  而且读者的深色模式、字号、阅读宽度全对不上。时序图、结构图、对比图都能用 mermaid 表达。
- **图注不是作者写的**：站点按图表类型自动生成（mermaid 时序图 → 「Sequence 图示」），没有自定义入口。所以图必须自解释：正文用「如下图所示」把要看的那条路径说出来，图内用 `Note over` 标注关键差异；别指望图注替你解释。
- 图要承担一次“说清三层关系”的活；只用来装点版面的图删掉，它会让读者以为那里有信息。
- 每篇至少 3 条外链，锚文本写清点过去能看到什么（规范原文、论文、官方文档、源码），并把三条 URL 先
  用 `curl -o /dev/null -w '%{http_code}'` 确认可达——断链比没有链接更伤。
- 位图（截图、照片）在站点具备资产管线前不可用：相对路径的图会被整段丢弃。需要视觉表达时用 mermaid
  或表格。**契约不写工具做不到的条款**：做不到就写「暂不支持」，否则下一轮执行时只能往回缩。

## 写前：素材门槛

五类材料，至少一类才能写：一次判断失误（原以为 A，实测 B）／一组反常数字／一句真实对话（谁、在哪、
原话）／一个可执行动作／一次对照（两种做法差在哪）。一类都没有 → 不写，或写成 1500 字以内的记录。

三类文章材料要求不同：复盘型（事故、改造、踩坑）必须有一次具体误判；推演型（选型、方法论、趋势）
必须有可验证的边界和至少一个反例，不许编「当年我也踩过」的故事；说明型（机制、架构、规范）第一段
直接给定义与用途，按使用顺序展开，不硬加冲突钩子。

三问答不出就不写：读者是谁（「正在做什么的人」，不是「工程师」）；他自己会怎么描述这个问题；
他读完能做出什么不同的决定（不是「有所启发」）。只有「我做了一套流程」而没有「你该怎么判断」
→ 换角度，或不做。

## 两个维度：表象 / 内核

**表象**（可量化，结构向这套外部写作方法借，只搬结构不搬情绪强度）：
标题按四步出 3 个候选——定基准（原素材里的强句）→ 放大（抠掉内部限定词，把人群扩到「遇到同类
问题的人」）→ 回落（按正文能兑现的上限往回压）→ 比优劣（不如原句有力就用原句）。每个候选附
「承诺 / 兑现」两行，三检验：承诺能兑现、标题与内核同向、反差来自读者已有认知而非刺激词。标题里
别再用 `不是 X，而是 Y`，那个句式正文还要限量。禁用「一文读懂 / 深度解析 / 99% 的人不知道」。
开头四种入口轮换，同一系列连续两篇不用同一种：一句现场原话 / 一组反常数字 / 对象定义 / 他的处境。
「处境 + 痛点 + 承诺」三件套是 AI 指纹，命中就删掉第一段重来；前 120 字里必须有一句承诺。
骨架按类型：复盘型（症状 → 当时的判断 → 真相 → 判据）、推演型（常见做法 → 隐含假设 → 失效处 →
判据）、说明型（定义 → 机制 → 使用顺序 → 边界）。一段 4–6 句、不超过 250 字，一段只装一个论证
单元（现象 → 原因 → 反例或类比 → 判断）；段落之间不写过渡句，靠事实转场。全文只有 1–2 句「可引用句」。

小标题按体裁分：说明型 6–9 个（每节 400–600 字，靠结构和图分担负载）；复盘型、推演型 3–4 个（靠段落承载，
不靠切小节撑结构）。结尾也按体裁：说明型给「参考与延伸」（判断已在前置各节给过），推演型抬一层给边界，
复盘型给判据与代价；三类都不许用清单收尾。系列可以在正文前放一句系列定位（引用块 ≤2 行），
但正文开场仍要每篇不同，系列定位不许代替开头。
只搬结构，不搬情绪强度：封面、平台适配、焦虑式钩子是短视频语境，技术博客的信任来自兑现。

**内核**（不靠技巧，靠材料）：故事 = 一次具体的误判，有时间、当时的判断、后来发现错在哪，
不是「我曾经遇到一个问题」；经验 = 亲手做过并改过，没跑过的不说跑过；判断 = 给结论、给边界、
给反例，只给视角不给判据的段落删掉。

## 事实纪律（一段）

事实层（数字、时间、命令、事件先后、人名仓库名）只许照抄，不许新增；判断层新增的因果与评价写
`推断：` 并给依据；两者都做不到就不写。

**语义强度锁**：拆句或提炼判断时保留原材料的条件、例外、否定与承诺强度。三类升级一律禁——概率
（可能/往往 → 保证/必然）、程度（缓解/降低 → 解决/根除）、范围（在 X 下有效/本次实测 → 全部/
普遍适用）。每写完一节回查原句的条件状语与否定词。

**改写旧稿时，原稿里的每个数字都当成未验证的**：改写是错误统计被原样继承的高危场景。核对要脚本化
——抽出新稿所有数字 token，逐个在原始 run-log / ledger / 报告里检索，缺一个就回源查。直接跑
`scripts/fact_check.py <draft.md> --corpus <dir-or-file> …`，输出里出现 MISS 就说明有一个数字说不清出处。

## 数字：先分性质，再谈密度

精确数字有两种，规则不同。判据只有一句：**读者能不能把它拿去用？**

- **参数型**：读者能拿去用的量——`20 字节`、`8 个字节`、`7 次握手`、`5,000 节点`、`4KB 页`。这类可以密集：
  参考博客实测都在 9–10 个/千字，解释型好文能到 15/千字。它们是知识，不是流水账。
- **证据型**：支撑本文论点的对比——「16 份执行报告里 13 份写了偏差」「契约只有 27 行」。全篇 ≤3 处，
  每处紧跟在它支撑的那一句后面；第四个就说明出现了第二个主张，该拆篇。
- **业绩型**：自己的产出——`16 份计划`、`776 行`、`2 小时 21 分`、`34 行账本`。这类数字一多，读者读到的
  就是汇报，注意力从观点移到「你干了多少」。处理：降成数量级（「上万行」「十几份」「大半晚」），全篇
  ≤3 处，且只留能撑论点的那一个。

**不要按总量设配额**。把密度一刀切压到 5/千字是过度校正——文字是干净了，但也丢掉了读者可以带走的参数。
真正的病是数字的**性质**，不是**数量**。

位置跟着性质走：参数型嵌在机制解释那一段；证据型紧跟主张；**业绩型不上标题、也不上前两段**，
全篇只留能撑论点的那一个。同一段出现三组以上精确数字，无论哪型都拆开。

落笔前逐个数字问「读者能拿走吗」：拿不走的，要么换成量级，要么删。场景与时间只留一个时刻（如「凌晨
一点半」），不放时间戳全串。

## 句子与段落（可计数）

单句 ≤55 字（引号内与行内代码不计，枚举清单不受限）。**不设句长均值**——按均值写会得到算法式的
均匀，那正是 AI 味；节奏靠长短交替，全文至少 3 句在 10 字以内。一句一组数字；同一对象同一名称；
专有名词保留英文（agent/cron/SHA256/Mermaid）；少用被动。

人称：「我」用于自己的判断、经历、失误；「我们」用于解释机制、标准、行业共识；不写第三人称自称「作者」——
个人博客里的「作者」像简历。术语首次出现写「中文（English、ABBR）」，之后只用中文或缩写；全文至少 3 处
括号对照，括号挂术语与条件，不做解释器。

## 语气：控制读者在哪停、往哪想

语气不是文风装饰，是节奏装置：它决定读者在哪里停半拍、在哪里被逼自己做判断。四种，各有位置和配额。

- **停顿**：独立成行的短句（≤10 字），放在结论之前或转折之后。全文 3–5 处。
- **反问**：放在读者需要自己做判断的位置（「你敢让它半夜自己改吗？」），不是开头钩子；不许自问自答式
  排比。1–3 处。
- **降温**：给出强判断后紧跟一句限定或自嘲（「这条我没法证明」），防止读者抵触。1–2 处。
- **换气**：引用块、图、表、代码块都是断点。连续三段以上纯文字等于节奏失控，必须插入一个非段落元素。

两条硬约束：相邻两段不用同一种装置，全文至少两种；**删掉这个装置论证仍然成立**才算合格——
删了论证就塌的那句是在替论证，不是在控节奏，应当收回内核里写实。

## AI 味：按结构判，不按词表判

致命（命中即重写）：全文无一处犹豫；段段收束在金句上；结尾给可照抄的「协议」而正文论证的是
「不能简化」；知识全输出（术语与数据堆到没有一个是作者真用来想事的）。

处置总则：命中只准删减、退回素材原话或停下追问作者；禁止换同义句式换壳重造，也禁止按配额造假的
不对称。

常见（超阈值才改）：`不是 X，而是 Y` 800 字 ≤2；段首连接词（值得注意的是/事实上/此外/然而）
千字 ≤1；给概念造新名字整篇 ≤1 次；同一让步句式（诚然…但…）整篇 ≤1 次；升维词（本质上/归根结底
接一个大一号命题）0 次；自编靶子反驳 0 次（只留真实被问过的质疑，并写清是谁问的）；三段式排比 0；
段段结构对称。

体裁豁免：学术穷尽反驳、教程枚举对仗、短视频段段金句，不判。

## 自检三轮

- 表象轮：开头入口是否立住（不是三件套）、承诺是否在前 120 字；标题是否兑现；每节标题能否独立读懂。
- 内核轮：有没有一次具体误判；删掉任意一节论证是否塌；回报是不是可执行动作。
- 文字轮：句长统计（脚本跑，不看感觉）、禁写计数、数字逐个归入参数/证据/业绩三类、语气装置计数
  （停顿/反问/降温/换气）与相邻段是否重复同一种、是否出现连续三段以上纯文字、图与外链条数、
  指认一处没验证的假设并说明它影响哪一节的结论（写成免责声明算 FAIL）、每节标题能否独立读懂。

## 契约本身也要被审

怀疑「文章还是不及格」时，先别继续改句子，把契约本身交出去审。

把站点的写作契约、目标文章、参考方法（外部写作方法的 plain-writing / ai-check / title 三份全文）
一起喂给一个异族模型，只问三件事：

1. 哪三条最可能让文章依然不及格——每条必须回答同一个问题：按这份契约，依然失败的原因是哪一条。
2. 哪些判据比参考方法弱（我们有这个动作但阈值更松）、哪些是对方有而我们完全没有。
3. 有没有立场冲突而对方是对的——要求它直接说我们错在哪。

两条硬要求：建议必须带可直接替换的文本，没给就不收；契约改动也交给模型执行（喂现状 + 评审
意见，要它输出完整文件），agent 只做事实核对、行数上限、lint 与落盘——手改会把模型刚写出的句子
层次磨平。

审两次都会命中的三条：把「必须有一处不确定」写成计数配额（模型用免责声明凑数）；开头三句模板
其实就是 AI 指纹 #16；按句长均值写的均匀本身就是 AI 味。修法见第 5、6 节。

落盘前必查：行数上限、章节标题里的数字是否跟着改（「两类文章」变三类时标题最容易漏）、
markdownlint、站点的本地构建。

## 写前规划：缺这一层，从零重写照样是流水账

事实清单干净、旧稿没喂、相似度 35%，文章仍然可能读起来像档案。病根在清单的**组织轴**：按项目阶段
（评审 → 计划 → 执行 → 契约）编号，模型只能照着阶段写，每节堆该阶段的事实，末尾补一句判断。读者拿到
的是时间线，不知道哪件事重要。

动笔前先落一份 `写前规划`（任务目录里的 `NN-preplan.md`），交给成稿模型之前自己写：

1. **读者与他脑子里那句话**（JTBD 任务陈述）：`当我正在 X，我想推进 Y，以便 Z`。写成「正在做什么的人」，
   并写清他自己会怎么描述这个问题。
2. **他读完能做出的决定**：具体到今晚写什么、改哪条配置；写不出就是选题不合格。
3. **一句话核心主张**：装不下第二个主张。
4. **承重事实表**：每条标「删掉哪节论证会塌」，只留 5–8 条。
5. **明令不用的清单**：把所有「好例子但不是承重墙」的数字列出来禁止出现。模型会本能用掉清单里每个事实，
   不点名禁止就一定全写进去。
6. **结构按冲突组织，不按阶段**：场景 → 当时的判断 → 三幕冲突 → 真相 → 判据 → 边界。三幕每幕写「发生了什么
   / 执行者当时怎么办」，段尾禁止加「这说明……」。
7. **验收清单**：把「第一段有具体时刻」「第 2 节写的是赌错了什么」「不许出现 X/Y/Z 数字」写成可打勾的条目。

用这套外部方法的 content-value 检查（开头能否留人 / 这件事和谁有关 / 观看回报 / 停留与转发）与
JTBD（任务陈述、切换的推力与焦虑）做诊断，只借框架，不搬文案。

流水账的可测量信号（`scripts/flow_check.py` 直接跑，四项里命中两项以上就先去改结构）：

- `sent_per_para` 长期 < 3：论证被切碎，一段只装半个主意；
- `scene_markers` = 0：全篇没有具体时刻/动作，读者没有代入位置；
- 六成以上段落收在判断句上：报告结论味，不像一个人想明白了一件事；
- 代码块 ≥ 4：正文被例子切碎。

**数字密度不要单独当判据**：解释型好文（如 draven）同样能达到 15/千字，它的数字是在替论点做量化；
判据是数字的“功能”而不是“数量”，见上一节。

## 从零重写：把旧稿从输入里删掉

触发：「完全重写」，或你发现上一版只是重构。把旧稿当事实来源喂进去，模型会沿用里面写得顺的句子，
交回一篇换了骨架的旧文。

做法是**只给事实清单，不给旧稿正文**。prompt 四块，缺一块就退回：

1. 任务与禁令：不许新增数字/事件/引文；只输出正文，无标题、无 frontmatter、无解释。
2. 结构指定：入口类型、骨架、篇幅、文末三条；把频道契约改写成命令式短句，不贴整份站点写作契约
   （整份贴进去模型会跳读，实测只遵守最后几条）。
3. 原文材料：代码块、契约原文、账本行、现场原话。这些本来就该逐字出现，给原文比给转述安全。
4. 事实清单 F01–Fn + 允许的推断 I01–In + 一条未验证假设（写明影响哪节）。

事实清单的写法：一条一个事实（时间、数字、谁做了什么、结果分布），编号但不需要正文引用；把旧稿
里的叙述句改写成陈述句（「16 份 summary 里 13 份写了偏差」而不是「账本看着很完美，但…」）。同一
事实只写一次——正文重复两次说明模型没读到，不是要你复制。

上限：事实清单占 prompt 三成左右。清单比正文还长时，先把事实合并（同源数字归一条），再补材料块。

验证（每项都跑）：

- `scripts/zh_draft_check.py draft.md --old old.md` → 相似度、逐字复用句、句长、禁写计数。
- 复用句逐条看：只该是推断句、引用块、文末固定三条。出现旧稿叙述句 = 没洗干净。
- `scripts/fact_check.py` 追每个数字；重写不会让旧数字变对。
- 标题数字精确优先；用量级（「一万行」代 10,866）时，正文第一屏必须给精确值。
- **不发布也能预演渲染**：把 frontmatter + 正文写进临时目录（`<task>/build-test/content/x.md`），跑
  站点的本地构建命令（`<site build> --content <task>/build-test/content --out <task>/build-test/dist`），
  再对产物 grep 四件事：`<h1`（标题是否单行）、`data-diagram="mermaid"`（图有没有渲）、`href="https://`
  （外链条数）、`\\_`（下划线转义是否为 0）。这一步把标题断行、图、外链、转义四类问题在 push 前一次查掉。
- **契约改动要用新体裁验收，不要反复改同一篇**：改完契约，挑一个此前没被测过的体裁（复盘篇改完就写说明篇）
  从零写一篇，量同一组指标并与旧稿对照（节数、每节字数、图、外链、问句、数字性质、段句数）。
  同一篇改三遍只会得到“这篇合格”，证明不了契约能指导下一篇。

坑：

- **标题会在词内断行**：站内 H1 一行约 11–12 个汉字，长标题会在「教会」这种词中间断成「教 / 会」。
  定稿前用 Range API 量断点，别靠肉眼：逐字 `setStart/setEnd` 取 `getBoundingClientRect().top`，top 变化处
  就是断行点；断在词中间就换标题或压到一行。理想是断在逗号处，最好是一行放下。
- **静态托管常有边缘缓存（如 600 秒）**：推完读回要带 `?cb=<ts>` 或看响应头 `age: 0`，否则会读到旧标题并误判没生效。
- **渲染器会转义正文里的裸下划线**：`sync_fail()` 不带反引号，线上显示成 `sync\_fail()`。含
  `_` 的标识符一律进反引号；build 后 `grep -c '\\_' dist/**/index.html` 应为 0。
- **句长计数器会把枚举行算成超长句**：结果分布、字段清单、账本行都属于契约豁免的枚举。别为迁就
  计数器去拆句子，`zh_draft_check.py` 给这类行标 `[ENUM]`，只改 `[FIX]`。
- **入口必须换**：上一版用反常数字，这一版就换现场原话或账本行。重写同一篇也算「同系列连续两篇」，
  入口重复等于同一篇换措辞。
- 低推理档出 3000 字约 1–2 分钟；同一个 prompt 换高推理档要 10–15 分钟，而且文字更均匀——这个
  耗时差本身就是“成稿不该开高推理档”的证据。后台 CLI 在 stderr 报 `not a terminal` 一类告警不是
  失败，产物照常写出。等后台任务完成通知（或轮询任务状态），别用前台 `sleep`（前台命令超时会被
  误读成生成失败）。
- **细节改拆长句会拆出残句**：把「以前不管 A，也不管 B。只要 C，就 D。」机械拆成两句，前一句变成没有主句的
  悬空从句。拆完逐句读一遍主谓是否完整；读着别扭就整句重写，不要继续在碎片上打补丁。
- **模型会自己给每节加一句独立金句**：一份 7 节的稿子会收到 4 句“一句一段”的收束句，那正是 AI 味的核心指纹。
  细节改的 prompt 里点名保留哪 1–2 句、删哪几句，并说明删掉的位置直接接下一段、不许补过渡句。
- **改指代前先核实指代对象**：让模型把「第 4 节」改成「上一节」时，先确认那一段说的确实是上一节；同节自指
  要改成「本节」。写错方向比不改更糟，读者会去翻一个不存在的位置。
- **术语的英文展开会吃掉 55 字预算**：`可移植操作系统接口（Portable Operating System Interface，POSIX）`
  一句就 60+ 字。把英文名放进独立的短句，或当缩写在读者群里已通用时只给中文释名，靠其它术语的括号凑够 3 处。
- **参考资料行会被句长检查报 `[FIX]`**：以 `- [` 开头的链接行，URL 计入字数。这类行一律当豁免，别为了把
  计数器压绿去把锚文本删到失真——锚文本的要求是“写清点过去能得到什么”。

## 发布：预演 → publish-set 闸门 → 线上回读

push 完不等于发布完。站点对「已发布集合」常有复核闸门，带 release 标记的构建在集合变化时直接失败：

```
release blocked: publish set changed (1 added, 0 removed);
run the site's review step, inspect the diff, and commit it
```

处理顺序固定：

1. 本地预演渲染（临时目录 + 站点构建命令，grep 四个标记），把标题断行、图、外链、转义在 push 前查掉。
2. push 之后 CI 若是这一步失败，跑站点仓库的 review 脚本（通常带 `--content .`）；它会写集合锁文件
   （例如 `.publish-set.json`）。
3. **看 diff 再提交**：应当只有新增 slug 一行。跑 `git diff <集合锁文件>`，确认没有别的任务顺带把草稿塞进集合，
   然后 commit + push，CI 才会通过。跳过复核闸门等于绕过发布审阅，别用别的路强行部署。
4. 上线后带 `?cb=<ts>` 回读，核对 `<h1>` 是否单行、`data-diagram`、外链条数、`\_` 转义、以及 `rel="prev"` 这类
   双链标注；mermaid 是客户端懒渲染，滚动到图的位置再看 SVG 是否出现（静态 HTML 里只有 `figure.diagram` + 源码块）。

**CI 失败先分清是内容还是上游**：`gh run view <id> --log-failed` 看死在哪一步。发布 action 会在构建前装 secret
scanner 之类的外部二进制；那一步 `curl: (22) ... 504` 是上游不可达，不是稿子有问题，重跑即可，别去改正文。

**等待上游恢复时，探针要跟重定向**：这类下载端点健康时返回 `302`，故障时才是 `504`。只用 `-w '%{http_code}'`
不加 `-L` 并要求等于 200，会把恢复窗口全判成失败。正确探法是能真的取到东西：
`curl -sL -o probe.bin -w '%{http_code} %{size_download}'`，再校验大小与 sha256，通过后再触发重跑。

## 交付前常犯

- 用自己的规模数字当开头招牌（多少份、多少行、多少小时）——读者不关心，放第二节当证据。
- 六节标题全是论断句，连读像目录；挑一节改成场景或问句。
- 把几次硬停写成几个成功案例；硬停里最值钱的是「当时心里没底」。
- 用「我做了 1、2、3」的流水账撑篇幅，而材料里其实有一次真正的误判没写。
